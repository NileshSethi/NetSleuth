## Abstract

NetSleuth Lite is a small Python tool that reads network flow log files in the style
used by Amazon Web Services (AWS) Virtual Private Cloud (VPC). The tool applies three
simple, rule-based detection checks to find suspicious traffic patterns, groups related
alerts into incidents, gives each incident a numerical risk score between 0 and 100,
and displays the results in an interactive web dashboard built with Streamlit.

The tool was built for a university course project to demonstrate how basic ideas from
the field of cybersecurity, specifically network traffic analysis and incident detection,
can be implemented in plain Python without machine learning and without any external
security platforms. Every detection decision made by the tool can be explained in one
sentence, which makes it suitable for a viva (oral examination).

The project was validated on five synthetic datasets generated by the same code.
All ten unit tests pass. All five benchmark scenarios produce perfect precision and
recall scores of 1.0. The honest interpretation of these results, and the limitations
of the approach, are discussed in the results section.

**Keywords:** network traffic analysis, intrusion detection, cloud security,
VPC flow logs, Python, Streamlit, MITRE ATT&CK, incident correlation.

## 1. Introduction

### 1.1 Problem Statement

When an organisation runs its applications on a cloud platform such as AWS, the cloud
provider records every network connection that flows in and out of the virtual machines.
These records are called flow logs. A single busy system can produce thousands of flow
log entries every minute. Looking through all of them by hand to find an attack is
impractical.

Automated tools exist to analyse flow logs, but most of them are large, expensive, and
opaque. When they raise an alarm, they often do not explain why. For a student learning
cybersecurity, and for a small team without specialist analysts, a simpler and more
transparent tool has value.

### 1.2 Project Goal

The goal of this project is to build a small, readable, and explainable tool that:

1. Reads a flow log CSV file.
2. Finds three specific types of suspicious behaviour using simple counting rules.
3. Groups related alerts into incidents and gives each a numeric risk score.
4. Shows everything in a web dashboard with a timeline and a network graph.

The project is not trying to compete with commercial security products. Its purpose is
to show that the core ideas of network threat detection can be expressed in a few
hundred lines of plain Python, and that every decision the code makes can be explained.

### 1.3 Scope

The tool reads flow logs that follow the format used by AWS VPC Flow Logs. It detects
three attack patterns: port scanning, host scanning, and data exfiltration. It does not
use machine learning. It does not connect to any external service. All processing
happens locally on the user's machine.

## 2. Background and Related Concepts

### 2.1 AWS VPC Flow Logs

Amazon Virtual Private Cloud (VPC) is the networking layer of AWS. It lets users
define their own private network inside the cloud. VPC Flow Logs is a feature that
records information about every network packet that enters or leaves a network
interface inside a VPC.

Each flow log record is a row containing fields such as:

- Timestamp: when the connection happened.
- Source IP: the machine that sent the data.
- Destination IP: the machine that received the data.
- Destination port: the specific service on the destination machine (for example,
  port 80 is HTTP, port 443 is HTTPS).
- Protocol: TCP or UDP.
- Bytes: how much data was transferred.
- Action: ACCEPT (allowed) or REJECT (blocked).
- Direction: INBOUND, OUTBOUND, or INTERNAL.

NetSleuth Lite reads CSV files that contain these fields.

### 2.2 Types of Network Attacks Detected

**Port Scan (MITRE T1046 — Network Service Discovery)**

A port scan is when an attacker sends connection requests to many different ports on a
single machine in a short time. The attacker is trying to find which ports are open,
because open ports indicate services that might have vulnerabilities. NetSleuth Lite
flags a source IP as a port scanner if it contacts 10 or more distinct ports on the
same destination host within 60 seconds.

**Host Scan (MITRE T1018 — Remote System Discovery)**

A host scan (also called a network sweep) is when an attacker probes many different
machines on the same port in a short time. The attacker is mapping the network to find
out which machines are running a particular service (for example, all machines with
SMB file sharing open on port 445). NetSleuth Lite flags this if a source IP contacts
5 or more distinct destination hosts on the same port within 60 seconds.

**Data Exfiltration (MITRE T1048 — Exfiltration Over Alternative Protocol)**

Exfiltration means stealing data out of a network by sending it to an external
destination. NetSleuth Lite flags this if a source IP sends 500,000 bytes (500 KB) or
more to the same external destination in a 120-second window, and the direction of those
flows is marked OUTBOUND.

### 2.3 MITRE ATT&CK Framework

MITRE ATT&CK is a publicly available knowledge base that lists the tactics and
techniques that real attackers use. Each technique has an identifier, for example T1046.
Mapping a detected event to a MITRE identifier helps analysts understand what stage of
an attack they are looking at.

The three techniques mapped in this project are:

| Technique ID | Name | Tactic | Kill Chain Stage |
|---|---|---|---|
| T1046 | Network Service Discovery | Discovery (TA0007) | Reconnaissance |
| T1018 | Remote System Discovery | Discovery (TA0007) | Lateral Movement Prep |
| T1048 | Exfiltration Over Alternative Protocol | Exfiltration (TA0010) | Actions on Objectives |

## 3. System Design and Architecture

### 3.1 Pipeline Overview

The tool processes data in one direction, from input to output. There is no feedback
loop or learning. The pipeline has five stages:

```
CSV File
   |
   v
loader.py  (load_flows)
   - Reads CSV
   - Validates columns, IPs, ports, bytes
   - Drops malformed rows
   - Converts timestamps to UTC
   |
   v
detectors.py  (run_all_detectors)
   - detect_port_scans
   - detect_host_scans
   - detect_exfiltration
   - Returns list of alert dictionaries, sorted by time
   |
   v
incidents.py  (build_incidents)
   - Groups alerts by source IP
   - Merges alerts within 5-minute windows
   - Calculates risk score (0-100)
   - Adds MITRE mapping and remediation steps
   |
   v
graph.py + evaluation.py
   - Network topology graph (Plotly + NetworkX)
   - Precision/recall evaluation table
   |
   v
app.py  (Streamlit dashboard)
   - Five tabs: Incidents, Timeline, Topology, Flow Telemetry, Forensic Dossier
```

### 3.2 Module Responsibilities

| Module | Responsibility |
|---|---|
| `config.py` | All numeric thresholds, scoring constants, and MITRE metadata. No logic. |
| `loader.py` | Read CSV, validate, clean, and sort. Returns a pandas DataFrame. |
| `detectors.py` | Three independent detection functions plus one that runs all three. |
| `incidents.py` | Group alerts, compute score, generate forensic dossier text. |
| `evaluation.py` | Compare detected flow indices against ground-truth labels. |
| `synthetic.py` | Generate five deterministic test datasets. |
| `graph.py` | Build a directed NetworkX graph and plot it with Plotly. |
| `app.py` | Streamlit page layout and user interface. |

### 3.3 Key Design Choices

**All thresholds are in one file.** `config.py` contains every numeric constant.
Changing a threshold requires editing exactly one number in one file.

**Zero label leakage.** The `label` column that exists in synthetic CSV files for
evaluation purposes is never read by any detector or incident function. The detectors
look only at traffic fields. This is verified by unit test 9.

**Explainable scoring.** The score is calculated step by step, and each step is
recorded in a list called `breakdown`. The dashboard shows this list to the user so
they can see exactly how the score was calculated.

## 4. Detection Rules

### 4.1 Port Scan Detector

**File:** `src/netsleuth/detectors.py`, function `detect_port_scans`

The detector groups all flow records by (source IP, destination IP) pairs. For each
pair, it scans the rows in time order using a sliding window of 60 seconds. When the
window contains 10 or more distinct destination ports, an alert is created and the
window pointer jumps past all the rows in that window to avoid counting them twice.

**Trigger:** Source IP contacts >= 10 distinct ports on one host within 60 seconds.  
**Severity:** MEDIUM  
**MITRE:** T1046

### 4.2 Host Scan Detector

**File:** `src/netsleuth/detectors.py`, function `detect_host_scans`

The detector groups all flow records by (source IP, destination port) pairs. For each
pair, it scans the rows in time order using a sliding window of 60 seconds. When the
window contains 5 or more distinct destination IPs, an alert is created.

**Trigger:** Source IP contacts >= 5 distinct hosts on one port within 60 seconds.  
**Severity:** MEDIUM  
**MITRE:** T1018

### 4.3 Exfiltration Detector

**File:** `src/netsleuth/detectors.py`, function `detect_exfiltration`

The detector first filters the DataFrame to keep only rows where `direction == "OUTBOUND"`.
It then groups by (source IP, destination IP) pairs. For each pair, it scans the rows
using a sliding window of 120 seconds and sums the bytes. If the sum reaches or exceeds
500,000 bytes, an alert is created.

**Trigger:** Source IP sends >= 500,000 bytes to one external host in 120 seconds,
with direction = OUTBOUND.  
**Severity:** HIGH  
**MITRE:** T1048

## 5. Incident Correlation and Risk Scoring

### 5.1 Incident Grouping

**File:** `src/netsleuth/incidents.py`, function `build_incidents`

After all alerts are generated, they are grouped by source IP. Within each source IP
group, alerts are sorted by start time. An alert is added to the current incident if
the gap between the end of the previous alert and the start of the new alert is at most
300 seconds (5 minutes). If the gap is larger than 300 seconds, the current incident is
closed and a new one starts.

This means that a multi-stage attack where an attacker pauses less than 5 minutes
between steps is recognised as one incident.

### 5.2 Risk Score Formula

**File:** `src/netsleuth/incidents.py`, function `score_incident`

The score is calculated in three additive steps and capped at 100.

**Step 1 — Base score.** The highest severity among all alerts in the incident
determines the starting points: LOW = 10, MEDIUM = 30, HIGH = 50.

**Step 2 — Extra alert bonus.** For each alert beyond the first in the incident,
10 points are added (up to the cap).

**Step 3 — Volume bonus.** If the total exfiltrated bytes in the incident is at least
5,000,000 (5 MB), add 20 points. If it is at least 500,000 (500 KB) but less than 5 MB,
add 10 points.

**Cap:** `min(100, base + extra + volume)`

**Example from Scenario 4:**
- Highest severity: HIGH -> base 50
- 2 additional alerts -> 2 x 10 = 20
- Exfil bytes: 6,300,000 >= 5,000,000 -> bonus 20
- Total: min(100, 50 + 20 + 20) = 90 -> Critical

**Risk level bands:**
- 0 to 29: Low
- 30 to 59: Medium
- 60 to 79: High
- 80 to 100: Critical

## 6. Dashboard and Visualisation

**File:** `app.py`

The dashboard is a Streamlit web application with five tabs.

### Tab 1 — Threat Incidents
Shows one card per incident. Each card displays the source IP, risk score, risk level
badge, MITRE kill chain progression, the explainable score breakdown, affected hosts,
and a recommended containment playbook.

### Tab 2 — Attack Timeline
Shows a scatter plot with time on the x-axis and kill chain stage on the y-axis.
Each point is one alert. Colour encodes severity (yellow = MEDIUM, red = HIGH).
Below the plot, a table shows all alert details including MITRE reference.

### Tab 3 — Network Topology
Shows a directed graph where each node is a host IP and each edge is a communication
channel. Red nodes are confirmed attacker IPs, orange nodes are targeted hosts, and
cyan nodes are normal hosts. A table next to the graph shows the top 8 communicating
IP pairs by data volume.

### Tab 4 — Flow Telemetry
Shows three charts: protocol distribution (pie), firewall action distribution (pie),
and top destination ports (bar chart). Below the charts is an interactive table where
the user can filter flows by IP address, direction, and firewall action.

### Tab 5 — Forensic Dossier and Evaluation
On the left side, a forensic dossier is generated for the first incident. The dossier
is a structured markdown document with an executive summary, MITRE kill chain table,
score breakdown, alert timeline, and remediation recommendations. The user can download
it as a .md file. On the right side, the evaluation table shows precision, recall, and
F1 score for all five benchmark scenarios.

## 7. Experimental Setup and Synthetic Data

### 7.1 Why Synthetic Data

No real network traffic was used because sharing real traffic logs requires permission
and raises privacy concerns. The synthetic data is generated by `synthetic.py` using a
fixed random seed (42) so results are exactly reproducible.

### 7.2 Benign Traffic Model

Background (normal) traffic is a mix of four types:

| Type | Port | Protocol | Bytes/flow |
|---|---|---|---|
| Web browsing (HTTP/S) | 80 or 443 | TCP | 800–15,000 |
| DNS lookup | 53 | UDP | 64–256 |
| SSH session | 22 | TCP | 500–3,000 |
| Email send (SMTP) | 587 | TCP | 1,200–6,000 |

Source IPs are drawn from `10.0.1.{10, 20, 30, 40}`. Inter-arrival time is 2–6 seconds.

### 7.3 Attack Scenarios

**Scenario 1 — Port Scan**  
External IP 198.51.100.55 probes 18 distinct ports on 10.0.1.20 in 17 seconds,
mixed with 220 benign flows. Total: 238 flows.

**Scenario 2 — Host Scan**  
Internal IP 10.0.1.15 probes 12 hosts on port 445 (SMB) in 22 seconds,
mixed with 220 benign flows. Total: 232 flows.

**Scenario 3 — Data Exfiltration**  
Internal IP 10.0.1.45 sends 4 x 600,000-byte flows to 203.0.113.88 in 24 seconds.
Total transfer: 2,400,000 bytes. Mixed with 220 benign flows. Total: 224 flows.

**Scenario 4 — Multi-Stage Attack**  
Single attacker IP 10.0.1.99 performs all three stages within one 275-second window:
port scan (Stage 1 at T+60s), host scan (Stage 2 at T+180s), exfiltration
(Stage 3 at T+300s). Total attack flows: 27 (13 + 8 + 6). Mixed with 250 benign flows.
Total: 277 flows.

**Scenario 5 — Benign Baseline**  
320 normal flows with no attack. Expected result: zero alerts, zero incidents.

### 8.3 Evaluation Metrics

Each alert contains the row indices of the flow records that triggered it.
The evaluation function compares these indices against the ground-truth label column.
A flow is a True Positive (TP) if it is labelled as attack and its index appears in
an alert. It is a False Positive (FP) if it is labelled as normal but flagged.
It is a False Negative (FN) if it is labelled as attack but not flagged.

| Scenario | TP | FP | FN | Precision | Recall | F1 |

| 1 — Port Scan | 18 | 0 | 0 | 1.0000 | 1.0000 | 1.0000 |
| 2 — Host Scan | 12 | 0 | 0 | 1.0000 | 1.0000 | 1.0000 |
| 3 — Data Exfiltration | 4 | 0 | 0 | 1.0000 | 1.0000 | 1.0000 |
| 4 — Multi-Stage Attack | 27 | 0 | 0 | 1.0000 | 1.0000 | 1.0000 |

## 10. Limitations and Honest Assessment

### 10.1 Why the Evaluation Scores Are Perfect

The synthetic data was generated by the same code that sets the detection thresholds.
Each attack pattern was designed to exceed the threshold by a comfortable margin.
Each benign flow was designed to stay below the threshold. This guarantees perfect
results on these specific datasets.

These results do not mean the tool would work perfectly on real network traffic.
In practice, real traffic is noisier, attack patterns are more varied, and the
thresholds would need to be tuned for the specific environment.

### 10.2 Other Limitations

1. **No machine learning.** The tool cannot learn from new patterns or adapt over time.
   It can only detect the three specific patterns for which it has rules.

2. **Fixed thresholds.** The thresholds in `config.py` were chosen to match the
   synthetic data. On a busy production network, normal users might legitimately
   trigger the port scan or host scan rules, causing false alarms.

3. **No real data used.** All testing was done on synthetic data. The tool has not been
   tested on real AWS VPC Flow Logs.

4. **Only three attack types.** Many common attacks, such as brute force, SQL injection,
   and DDoS, are not covered.

5. **Exfiltration requires OUTBOUND direction.** Large internal transfers are not flagged.

6. **No authentication.** The dashboard has no login. Anyone who can access the URL can
   see all incident data.

## 11. Conclusion

NetSleuth Lite demonstrates that three common network attack patterns can be detected
from flow logs using simple Python code. The tool reads a CSV file, applies three
counting rules, groups the resulting alerts into incidents, calculates a risk score,
and presents everything in a web dashboard.

Every detection decision can be explained in one sentence. Every score can be
reconstructed by hand. The code is 1,671 lines across nine files. All 10 unit tests
pass. All five synthetic benchmark scenarios produce correct results.

The main contribution of this project is not a novel algorithm. It is a clear,
readable, and fully transparent implementation that a student can understand,
explain in a viva, and extend with additional rules in the future.
